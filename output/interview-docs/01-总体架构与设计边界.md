# FinalWeek 总体架构与设计边界

## 1. 项目解决什么问题

期末复习资料通常分散在课件、教材 PDF、教师录音、课程视频、历年真题和个人笔记中。普通聊天模型面临三个问题：无法直接理解多种文件格式，回答缺少课程范围约束，生成内容难以追溯到原资料。

FinalWeek 的核心不是“聊天”，而是先建设课程级知识底座，再让多个 AI 功能消费这套知识：

```text
多模态资料
  -> 统一解析与来源定位
  -> CourseSegment
  -> Qdrant + Lucene 双索引
  -> 混合检索
  -> 提纲 / 计划 / 问答 / 模拟卷
```

## 2. 架构形态

项目采用前后端分离的模块化单体：

```text
Vue 3 + TypeScript
        |
        | REST / Chunk Upload / SSE
        v
Spring Boot 3.5（唯一权限和业务入口，单 JVM）
  |-- auth / course / upload / material
  |-- task / knowledge / knowledgeversion
  |-- outline / plan / chat / mockexam
  |-- ai provider adapters
        |
        |-- MySQL
        |-- Redis
        |-- RabbitMQ
        |-- MinIO
        |-- Qdrant
        |-- Local Lucene
        `-- Bailian + FFmpeg + LibreOffice + XeLaTeX
```

它不是微服务。选择模块化单体的原因：

- 项目是求职 MVP，核心难点是资料处理和 AI 工作流，不是服务治理。
- Web API 和 Consumer 共用领域模型、事务和本地 Lucene，单 JVM 能显著降低部署与一致性复杂度。
- Docker Compose 已经包含多个基础设施组件，继续拆业务服务会增加调用链、配置和排障成本，但短期没有独立扩缩容收益。

代价是：本地 Lucene 和单实例 Consumer 限制了横向扩容；如果演进到多实例，需要把关键词索引迁移到 OpenSearch/Elasticsearch，或建立可靠的索引写入与分片协调机制。

## 3. 各存储的职责边界

### MySQL：业务与任务真相源

保存用户、课程、资料、知识片段、知识版本、提纲、计划、聊天、模拟卷、后台任务和 checkpoint。

关键原则：

- 最终业务状态以 MySQL 为准。
- 权限判断必须回到 MySQL，以 `userId + courseId` 过滤。
- Redis、Qdrant 和 Lucene 都不能单独证明业务结果已经成功。
- 通过事务、唯一约束、行锁和 compare-and-set 控制并发写入。

### Redis：临时状态与协调

承担 Session、验证码、上传元数据、已上传分片集合、分布式锁、限流和 SSE 进度缓存。

选择 Redis 的原因是这些数据具有短生命周期、高频读写或原子协调需求。Redis 不保存课程和任务终态，避免缓存丢失变成业务数据丢失。

认证接口在 Redis 不可用时 fail closed，返回 503，因为 Session 和权限上下文无法可信恢复。公开落地页和健康检查仍可访问。

### RabbitMQ：后台任务调度

资料解析、提纲、计划、问答和模拟卷都统一为 `background_task`，通过 RabbitMQ 解耦 HTTP 请求和长耗时工作。

RabbitMQ 只负责消息传递；任务是否排队、执行、成功或失败仍以 MySQL 状态机为准。

### MinIO：大对象存储

保存上传分片、原始文件、归一化预览 PDF、解析中间结果和模拟卷 PDF。数据库只保存对象键与元数据，不把大文件写入 BLOB。

MinIO 与 MySQL 之间没有分布式事务。项目使用确定性对象键、数据库唯一约束、幂等覆盖和孤儿对象清理进行最终补偿。

### Qdrant 与 Lucene：可重建的派生索引

- Qdrant：存储 Embedding，处理语义相近但关键词不同的查询。
- Lucene：BM25 关键词召回，处理课程术语、专有名词和精确关键词。
- MySQL `course_segment`：保存最终展示的原文和位置。

检索命中后必须回查 MySQL，并过滤只属于当前用户、当前课程、解析成功资料的 segment。

## 4. 后端分层方式

后端以领域包组织，而不是把所有 Controller、Service、Repository 分别放进三个大目录。每个领域内部包含自己的入口、编排、实体和持久化接口。

典型调用关系：

```text
Controller
  -> Coordinator / Service
      -> Repository + Domain validation
      -> Task creation / dispatch

TaskConsumer
  -> TaskPipeline（按 TaskType 路由）
      -> Retrieval / AI client / Validator
      -> Publisher（事务发布业务结果）
```

`TaskPipeline` 是统一后台任务扩展点。新增任务类型时，需要增加 `TaskType`、允许的 `TaskStage`、对应 Pipeline 和状态收尾逻辑。

## 5. 前端架构

前端按课程的五个独立 URL 组织业务区：资料、提纲、计划、问答和模拟卷。公共 HTTP 层统一处理：

- Cookie Session；
- CSRF Token；
- 安全错误结构；
- 503 服务不可用事件。

Pinia 任务 Store 启动时先通过 REST 拉取活动任务，再连接 SSE。收到进度事件后重新读取任务详情。这个组合解决：

- SSE 只负责及时通知；
- REST 负责刷新后的状态恢复；
- 短时断线不会丢失任务终态；
- 用户离开业务页面后，任务仍能在全局抽屉中追踪。

## 6. 横切设计

### 权限隔离

所有课程资源都按用户归属查询。Qdrant payload、Lucene document 和 CourseSegment 同时带用户、课程、资料维度；最终仍回查 MySQL。越权查询统一返回 404，避免泄露资源是否存在。

### 幂等

系统没有依赖某一把锁实现幂等，而是组合使用：

- 稳定业务键和稳定对象键；
- MySQL 唯一约束；
- CAS 状态更新；
- checkpoint；
- Qdrant/Lucene upsert；
- Redis 锁减少重复并发。

### 可恢复性

每个后台任务记录任务级状态和阶段级 checkpoint。外部 API 重试预算与 RabbitMQ 投递预算分开计数，避免两个循环相乘后产生不可控调用次数。

### 可追溯性

`CourseSegment` 统一保存页码、幻灯片号、段落号或起止时间。提纲节点、课程回答和模拟题保存 segment 引用，使生成结果可返回原资料位置。

## 7. 明确边界

面试中应主动说清：

- 单后端实例，不具备当前形态下的水平扩展能力。
- 没有使用 Outbox，也没有跨 MySQL、RabbitMQ、MinIO、Qdrant 的强事务。
- 限流参数是本地 Demo 保护值，没有生产流量校准。
- 没有多模型路由、联网搜索、Cross-Encoder 重排或复杂 Agent。
- Golden Case 证明固定样例下的功能质量，不等于线上生产质量。
- 项目重视失败可见和可恢复，但不能把它描述为生产级高可用系统。

## 8. 架构回答模板

面试官问“为什么用了这么多中间件”时，可以回答：

> 我不是按技术栈堆组件，而是按数据性质拆职责。MySQL 保存业务真相；Redis 处理短期状态、锁和限流；MinIO 保存大文件；RabbitMQ 把 OCR、Embedding、LLM 和 PDF 生成从 HTTP 请求中异步化；Qdrant 与 Lucene分别解决语义召回和精确关键词召回。这两类索引都被视为可重建数据，最终权限和原文仍回查 MySQL。项目当前是单实例模块化单体，这是我为求职 MVP 在工程完整性和部署复杂度之间做的取舍。
