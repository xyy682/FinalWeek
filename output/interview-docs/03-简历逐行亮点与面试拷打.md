# FinalWeek 简历逐行亮点与面试拷打

本文严格对应简历第三版中的 6 条 FinalWeek 项目亮点。建议每一条至少准备：30 秒概述、2 分钟深挖、一个故障场景和一个替代方案比较。

## 第一行：大文件稳定上传

> 基于 Redis + MinIO 实现分片上传与断点续传，使用 Redisson 合并锁控制并发 complete，并结合内容哈希与唯一约束避免重复合并、重复解析。

### 这行到底做了什么

- Redis 保存 upload 元数据、TTL、已完成分片 Set 和 completed 标记。
- MinIO 保存确定性键的分片对象和最终课程文件。
- 分片写入顺序是先 MinIO，后 Redis Set。
- complete 使用 `uploadId` 锁防止同一会话并发合并。
- 合并时流式计算 SHA-256，并校验文件大小、声明哈希和实际内容类型。
- 使用 `courseId + contentHash` 锁和数据库课程内哈希约束防止不同会话提交相同文件。
- MySQL 保存 `UploadCompletion`，Redis completed 丢失后仍可恢复幂等结果。

### 高频问题 1：为什么不直接使用 MultipartFile 一次上传？

回答要点：

> 文档可能达到 100 MB，音视频可达到 GB 级。一次请求失败需要整体重传，也会让反向代理、Servlet 请求和网络连接长时间占用。分片后每片可以独立重试，刷新后根据已完成分片集合补差集，失败成本从整个文件降到单个 chunk。

不要说“分片上传一定更快”；它主要提高可恢复性，也可以通过有限并发改善吞吐，但会增加状态管理、分片清理和 complete 幂等复杂度。

### 高频问题 2：为什么分片状态放 Redis，不为每个分片建 MySQL 表？

回答要点：

> 分片编号是高频、短生命周期、天然带 TTL 的临时状态，Redis Set 适合去重和集合查询。MySQL 保存上传归属与最终完成记录，负责可恢复的业务结果。如果需要严格审计每个分片或 Redis 长时间不可用后继续上传，才更适合把分片明细持久化到数据库。

### 高频问题 3：为什么先写 MinIO 再写 Redis？

> 如果先把编号写入 Redis，MinIO 写失败后状态会显示分片已完成，complete 可能读不到实际对象。先落对象再记完成，最坏情况是对象已存在但 Redis 未记录，客户端重复上传覆盖确定性键即可恢复。

### 高频问题 4：Redisson 锁能保证 complete 幂等吗？

> 不能只依赖锁。锁只减少并发执行。真正的幂等来自 Redis completed、MySQL UploadCompletion、课程内容哈希唯一约束、确定性对象键和重复查询返回原 Material。锁租约到期或进程异常时，数据库约束仍要兜底。

### 高频问题 5：为什么要两种锁？

- uploadId 锁：同一个上传会话只能有一个合并者。
- courseId + contentHash 锁：两个不同上传会话上传同一文件时避免同时创建资料。

即使存在第二把锁，数据库唯一约束仍是最终兜底。

### 高频问题 6：客户端上传前已经计算 SHA-256，服务端为什么还要算？

> 客户端声明不能作为可信依据。服务端必须对实际合并字节计算哈希，才能发现传输错误、错误分片顺序或恶意伪造，同时该哈希还用于课程内内容去重。

### 高频问题 7：complete 过程中 MinIO 成功、MySQL 失败怎么办？

> MinIO 和 MySQL 没有分布式事务。项目使用稳定对象键和管理员孤儿清理进行补偿，不能声称强一致。生产化可以增加对象状态表、定时 reconciliation，或先写临时对象，数据库成功后再标记/复制到正式前缀。

### 高频问题 8：为什么后端要合并到本地临时文件？会不会占磁盘？

> 当前解析工具和内容校验需要本地 seekable 文件，合并时还能流式计算哈希，因此 MVP 使用临时文件，finally 删除。代价是磁盘峰值约等于文件大小；生产化可限制并发 complete、监控临时盘、使用专用工作目录，或探索 MinIO Compose Object，但仍需解决内容嗅探和下游工具输入方式。

### 容易说错

- 不要说 Redis 保证最终上传状态，MySQL 完成记录才是恢复兜底。
- 不要说使用了分布式事务。
- 不要说锁绝对不会失效。
- 不要声称支持无限大文件；项目有明确大小和时长限制。

## 第二行：异步任务可靠性

> 将资料解析、提纲、计划和模拟卷统一接入 RabbitMQ 后台任务，结合 publisher confirm、manual ack、MySQL CAS、业务幂等键与阶段 checkpoint 支持失败重试和断点恢复。

### 这行到底做了什么

- 统一任务表承载 `PARSE_MATERIAL`、`GENERATE_OUTLINE`、`GENERATE_PLAN`、`ANSWER_CHAT`、`GENERATE_MOCK_EXAM`。
- 创建业务记录时同步创建 `PENDING_PUBLISH` 任务。
- 投递使用 persistent message、publisher confirm 和显式 `PUBLISH_FAILED`。
- Consumer manual ack，成功提交数据库状态后才 ack。
- MySQL CAS 抢占任务；终态、旧轮次和重复消息直接 ack。
- 通过 checkpoint 从最近完成阶段继续。
- Retryable 和 Permanent 异常分类处理，重试预算有限。
- `executionRound` 隔离手动重试前后的延迟消息。

### 高频问题 1：为什么要用 RabbitMQ，直接异步线程池不行吗？

> 线程池只能解耦当前请求线程，进程重启后排队任务会丢失，也缺少 durable queue、重投和 DLQ。RabbitMQ 更适合秒级到分钟级的 OCR、Embedding、LLM 和 PDF 生成任务。代价是要处理重复投递、消息与数据库不一致、消费幂等和运维复杂度。

### 高频问题 2：publisher confirm 解决什么，没解决什么？

> confirm 证明 Broker 接收了消息，降低“接口以为投递成功但消息丢失”的风险；它不保证消费者处理成功，也不保证数据库状态和消息原子提交。消费成功由 manual ack、任务状态和幂等逻辑负责。

### 高频问题 3：为什么不使用 Outbox？

> 当前 MVP 选择 `PENDING_PUBLISH + confirm + PUBLISH_FAILED + stale scanner`，代码和部署更轻，失败对用户可见且能重投。缺点是数据库提交后、消息发布前进程崩溃仍依赖扫描补偿。若进入生产并要求更严格的投递完整性，我会把任务事件写入本地 Outbox，在同一事务提交，再由独立 relay 投递 MQ。

### 高频问题 4：为什么不能只靠 RabbitMQ 的 messageId 去重？

> Broker 可能重复投递，应用重试也可能产生新 messageId；messageId 只能帮助识别某次消息。业务幂等必须落在数据库状态、business key、稳定实体 ID、唯一约束和 checkpoint 上。

### 高频问题 5：CAS 在哪里发挥作用？

> Consumer 只有把允许状态和当前 executionRound 原子更新为 PROCESSING 才能执行；取消、重投和旧任务发布同样通过条件更新竞争。这样即使多个线程同时收到重复消息，也只有一个能成功推进状态。

### 高频问题 6：manual ack 的时机是什么？

> Pipeline 完成、业务结果发布并且任务状态成功写入 MySQL 后才 ack。临时异常先更新 RETRYING，再 nack requeue；永久异常或预算耗尽写 FAILED 后 reject。不能在开始执行时 ack，否则进程中途崩溃会丢任务。

### 高频问题 7：checkpoint 为什么必须最后写？

> checkpoint 表示某阶段结果已经完整可用。必须先幂等写入阶段产物，再提交 checkpoint。反过来会出现 checkpoint 已完成但产物只有一半，重试跳过该阶段后无法恢复。

### 高频问题 8：为什么区分 API 重试和任务重投？

> 一次消费中模型 API 可能做短暂重试，整个任务还可能被 MQ 重投。如果共用模糊计数或嵌套无限重试，调用次数会乘法膨胀。分别设预算可以控制成本并解释日志。

### 高频问题 9：Consumer 执行成功但 ack 前连接断开，会怎样？

> RabbitMQ 会再次投递。Consumer 先检查 MySQL 任务状态，已经 SUCCEEDED 就直接 ack；阶段产物也使用稳定键和 upsert，因此重复消息不会重复发布业务结果。

### 高频问题 10：任务锁和 CAS 有什么区别？

> Redis 锁降低重复工作和外部 API 浪费，MySQL CAS 决定谁拥有合法状态迁移。锁可能过期或网络分区，不能替代数据库正确性检查。

### 容易说错

- 不要说“消息绝对不丢”；应说失败窗口可检测、可补偿。
- 不要说“exactly once”；实际是 at-least-once 语义下的业务幂等。
- 不要把 DLQ 当自动恢复；DLQ 是隔离和排查手段。
- 简历原句未提问答，但代码中问答也接入了隐藏后台任务，面试可补充说明。

## 第三行：多模态资料解析

> 使用 PDFBox、POI、FFmpeg 与 ASR/OCR 处理文档和音视频，将文本、页码、幻灯片号与时间戳统一沉淀为 CourseSegment，实现生成结果到原资料的定位回溯。

### 这行到底做了什么

- 每种格式实现统一 `MaterialParser` 接口。
- PDF 原生文本优先，低文字密度页才 OCR。
- PPTX 使用 POI 抽取，LibreOffice 生成预览 PDF，必要时 OCR。
- MP3 使用 FFmpeg/ffprobe 校验、切音轨并 ASR。
- MP4 合并音轨 ASR 与关键帧 OCR，关键帧使用感知哈希去重。
- 最终统一为带来源位置的 `ExtractedUnit`，再转为 `CourseSegment`。

### 高频问题 1：为什么不能所有 PDF 都直接 OCR？

> 原生 PDF 已包含高质量文本层，PDFBox 更快、更便宜且不会引入识别错误。只有低文字密度或扫描页才 OCR，形成按页 fallback。阈值是启发式配置，需要根据样本调优。

### 高频问题 2：PPT 为什么还要转 PDF？

> POI 负责提取文本和页级结构，LibreOffice 生成统一可预览的 PDF。这样前端不需要实现 PPT 渲染器，来源点击也有稳定的页/幻灯片展示载体。转换增加了外部进程依赖，需要超时和失败处理。

### 高频问题 3：MP4 怎么把音频和画面文字合在一起？

> 音轨经 ASR 得到句级时间戳；视频按场景和最大间隔抽关键帧，用感知哈希去掉相似帧，再 OCR。两路结果按时间区间合并为统一时间线。单路失败时保留另一条有效内容并记录 warning。

### 高频问题 4：为什么要感知哈希，不比较文件 SHA-256？

> 相邻视频帧的二进制字节几乎一定不同，但视觉内容可能相同。感知哈希比较视觉特征，可以减少重复 OCR 调用。它是近似判定，会存在阈值选择和误去重风险。

### 高频问题 5：CourseSegment 为什么是核心抽象？

> 它把 PDF 页、PPT 页、文本段落和媒体时间戳统一成一种可检索、可引用的知识单元。上层提纲、问答和出卷只面向 segment，不需要为每种文件格式写独立逻辑。

### 高频问题 6：为什么保留 ASR 文本和 OCR 文本，而不只存合并结果？

> 分路字段便于追踪来源、诊断识别质量和改进合并策略；统一 content 用于检索。如果只存最终字符串，出现错误时难以判断来自音轨还是画面。

### 高频问题 7：复杂公式、表格和图片怎么办？

> 当前 MVP 不承诺完整理解复杂公式、图表和纯视觉动作。OCR 能提取部分文字，但不能把所有视觉语义可靠结构化。面试要明确这是边界，不要把多模态解析描述成通用视频理解。

### 高频问题 8：解析过程如何恢复？

> 提取结果保存为 MinIO 中的确定性 `content-extracted.json`，成功后写 checkpoint；分块和索引也有独立 checkpoint。后续失败可以复用已经提取的上下文，避免再次执行昂贵 OCR/ASR。

### 容易说错

- 不要说视频被“大模型完整理解”，当前是 ASR + 抽帧 OCR。
- 不要说所有公式都能识别。
- 不要说来源定位绝对精确；它依赖解析器元数据和时间线合并质量。

## 第四行：课程级混合 RAG

> 采用 Qdrant 向量召回 + Lucene BM25 关键词召回，并通过 RRF 融合排序；检索按用户与课程强制隔离，为提纲和问答返回可验证的来源片段。

### 这行到底做了什么

- 文档分块批量 Embedding 后 upsert Qdrant。
- 相同 segment 同时写入课程级 Lucene 索引。
- 查询分别获得向量排名和 BM25 排名。
- RRF 融合、按 segment ID 去重并取 Final TopK。
- 回查 MySQL，只返回归属正确且资料状态为 SUCCEEDED 的原文。
- 单路故障自动降级，双路失败明确报错。

### 高频问题 1：为什么向量检索还不够？

> 向量适合语义近似，但对课程缩写、专有名词、公式符号和精确关键词未必稳定；BM25 对词项匹配更强。两路互补可以提高不同查询类型的召回鲁棒性。

### 高频问题 2：为什么用 RRF，不直接加权相加分数？

> 向量相似度和 BM25 分数不在同一量纲，直接相加需要归一化和调参。RRF 只依赖排名，工程上更稳健，也便于单路降级。缺点是忽略原始分数幅度，后续可以基于评测尝试归一化加权或 Cross-Encoder 重排。

### 高频问题 3：RRF 的 K=60 有什么意义？

> K 控制头部排名差异对融合分的影响。K 较大时各名次差距更平缓，降低单路第一名的支配程度。60 是常见默认值，本项目配置化但没有宣称经过大规模线上调优。

### 高频问题 4：为什么命中后还要回查 MySQL？

> Qdrant payload 和 Lucene 文档是派生索引，可能延迟、损坏或残留。MySQL 才能确认用户、课程、资料状态，并提供可信原文和位置。这也是防止跨课程数据泄漏的最后一道边界。

### 高频问题 5：索引写了一半任务失败，会不会检索到半成品？

> 可能存在部分派生索引，但查询回查数据库时只接受 Material 状态为 SUCCEEDED 的 segment。完整索引结束后才把资料标为成功，因此半成品不会出现在最终结果中。重复任务通过稳定 ID upsert 覆盖。

### 高频问题 6：Lucene 为什么需要课程级锁？

> 本地 Lucene IndexWriter 的课程增量写需要串行协调，项目使用本地锁与 Redisson 课程锁避免同一课程并发提交冲突。因为索引在本机，这也构成单实例部署约束。

### 高频问题 7：Qdrant 或 Lucene 挂了怎么办？

> 单路异常被记录并使用另一条结果；两路都失败才返回 503。降级提升可用性，但召回质量可能下降，所以日志中需要记录 degraded 状态。

### 高频问题 8：为什么没有 Cross-Encoder 重排？

> MVP 优先完成来源隔离、双路检索和完整业务闭环。Cross-Encoder 会增加模型成本和延迟，也需要有标注集验证收益。它是合理的下一步，不应在没有评测的情况下为了技术名词直接加入。

### 高频问题 9：chunk 大小和 overlap 怎么定？

> 当前使用可配置 token 上限和 overlap，先沿自然边界切分。chunk 太小会丢上下文并增加索引量，太大则降低定位精度、增加模型上下文成本。最终应结合课程问答命中率和引用正确率评测，而不是只凭经验。

### 高频问题 10：如何评估 RAG？

> 项目 Golden Case 关注知识点覆盖、引用正确、无依据陈述、结构合法性等指标。更完整的检索评测应单独构造 query-relevant segment 标注，计算 Recall@K、MRR/nDCG，再把检索指标和最终回答忠实度分开分析。

### 容易说错

- 不要把 Qdrant 称为主数据库。
- 不要说 RRF 一定优于所有重排方法。
- 不要说做了 Cross-Encoder 或向量数据库集群。
- 不要只说“按 courseId 过滤”，还要强调最终 MySQL ownership 校验。

## 第五行：知识版本与后台生成

> 将成功资料集合固化为不可变知识版本，使用版本指针与 CAS 避免旧任务覆盖新结果；计划、问答等耗时能力后台执行，支持 SSE/REST 恢复任务终态。

### 这行到底做了什么

- 用户确认时对全部成功资料的 ID 与哈希计算集合哈希。
- 创建不可变知识版本和版本资料映射。
- 新版本自动创建提纲任务。
- 提纲发布成功后才切换课程当前版本指针。
- 计划固定知识版本、提纲和预期计划版本，通过 CAS 发布。
- 模拟卷固定知识版本和提纲范围。
- SSE 负责及时通知，REST/MySQL 负责刷新和断线恢复。
- 问答后台执行，但检索当前全部成功资料，不完全等同于知识版本快照。

### 高频问题 1：为什么需要知识版本？

> AI 任务可能执行几十秒到几分钟。期间用户可能又上传资料或触发新任务。如果只查询“当前资料”，同一次生成的不同阶段可能看到不同集合，旧任务完成后也可能覆盖新结果。提交时固定 material 集合可以提供一致输入和可重现性。

### 高频问题 2：为什么不是上传成功后自动更新当前版本？

> 资料解析成功只说明单份资料可检索，不代表用户已完成本轮资料准备。显式确认把多个成功资料形成一个业务快照，同时允许用户确认忽略失败资料，避免提纲被频繁自动重生成。

### 高频问题 3：集合哈希解决什么？

> 将排序后的 `materialId + contentHash` 组成规范串再计算 SHA-256，可以快速判断成功资料集合是否变化，阻止重复确认相同版本。它不是用来加密资料，也不能替代版本号。

### 高频问题 4：版本指针和 CAS 如何避免旧任务覆盖？

> 任务创建时保存 generationVersion 或预期当前版本。发布事务只有在预期版本仍匹配时才替换当前指针；如果更新数为 0，说明已有新请求推进了版本，旧任务结果不再发布。

### 高频问题 5：为什么生成失败要保留旧结果？

> 异步 AI 服务天然可能超时或输出非法。先构建和验证新结果，成功后再切换指针，可以保证用户始终至少看到上一版可用结果，而不是生成一开始就删除旧数据。

### 高频问题 6：SSE 和 WebSocket 为什么选 SSE？

> 当前需求主要是服务器单向推送任务状态，不需要双向实时通信。SSE 基于 HTTP、浏览器原生 EventSource、断线重连简单。模型答案本身不做 token 流式输出，SSE 只承担状态通知。

### 高频问题 7：既然有 SSE，为什么还要 REST？

> SSE 连接可能中断，浏览器关闭时事件也不会被接收。状态变化先落 MySQL，SSE 只是提示；重连或刷新后通过 REST 查询活动任务与最终结果，才能恢复权威状态。

### 高频问题 8：为什么简历把问答也放在“版本与后台生成”里，但问答不固定知识版本？

> 这句话强调的是后台任务化。代码中的问答为了让新上传成功的资料立即可问，检索当前全部成功资料；提纲、计划和模拟卷更强调可重复生成，因此固定版本。面试中要主动区分，避免说成所有功能都读取同一个版本快照。

### 高频问题 9：为什么不直接保存每一版完整 segment 副本？

> 知识版本保存 material 映射，segment 仍属于不可变资料。这样避免每次版本复制大量文本；只要成功资料不做原地修改，版本就可以通过 material 集合重建上下文。代价是删除策略必须谨慎，所以成功资料只能随课程整体删除。

### 容易说错

- 不要说所有上层功能完全共享同一快照；问答是例外。
- 不要说 CAS 等于数据库分布式锁。
- 不要说 SSE 保证消息不丢。
- 不要把“不可变版本”说成物理复制全部索引。

## 第六行：结构化模拟卷

> 基于固定 JSON Schema + Java Validator 校验题型、答案、分值与来源，再通过受控 XeLaTeX 模板原子生成试卷/参考答案双 PDF，并完成浏览器主链路与 14 条真实 Golden Case 验证。

### 这行到底做了什么

- 请求归一化后固定题型、题量、整数分值、范围、时长和知识版本。
- LLM 必须按 JSON Schema 返回结构化 DTO。
- Java Validator 校验题目结构、题数、答案、分值总和、公式字段、来源白名单和严格资料模式。
- QualityChecker 检查直接复刻资料原题、历史卷相似度和提纲范围覆盖。
- 同一份已校验 DTO 分别渲染试卷和答案 TeX。
- XeLaTeX 使用固定模板、超时、日志大小限制和 `-no-shell-escape`。
- 本地 PDFBox 校验后上传 MinIO，再下载远端对象复核。
- 两份都成功才发布对象键；部分失败进行补偿清理。

### 高频问题 1：为什么必须结构化输出？

> 出卷需要确定题型、题数、分值、答案和来源，还要生成两份一致的 PDF。自由文本难以可靠解析和校验。JSON Schema 约束语法与字段，Java Validator 处理跨字段业务规则，两层职责不同。

### 高频问题 2：有 JSON Schema，为什么还需要 Java Validator？

> Schema 能校验字段类型、枚举和基本结构，但“所有题目分值之和必须等于总分”“选择题答案必须属于选项”“segment 必须来自本次上下文”“严格资料模式每题必须有来源”等需要数据库和跨字段信息，必须由应用层校验。

### 高频问题 3：模型输出非法怎么办？

> 模拟卷 Pipeline 将非法输出视为明确失败，不把未校验内容发布。提纲流程允许一次只修格式的模型修复；不能无限让模型自我修复，否则成本和结果不可控。

### 高频问题 4：怎么防止模型照抄真题？

> Prompt 明确只学习风格，QualityChecker 对标准化题干与来源文本做包含关系和二元 gram 重合检测，超过阈值直接拒绝；与历史模拟卷过于相似则产生 warning。这是启发式规则，不能声称能识别所有语义改写。

### 高频问题 5：为什么用 XeLaTeX，不直接用 HTML 转 PDF？

> 试卷包含中文、分页、公式和答案排版，XeLaTeX 的印刷质量和公式支持更稳定。固定模板还能保证试卷和答案风格一致。代价是镜像更大、编译较慢，并需要防止 TeX 注入和限制外部进程。

### 高频问题 6：怎样控制 XeLaTeX 安全？

> 使用非特权容器用户、固定模板、文本转义、公式白名单、`-no-shell-escape`、编译超时、日志大小限制、临时目录边界检查和产物大小/页数校验。不能把模型输出直接拼进任意 TeX 命令。

### 高频问题 7：“双 PDF 原子生成”是什么意思？MinIO 有事务吗？

> MinIO 没有跨两个对象的事务。这里是业务层原子发布：试卷和答案都本地生成、校验、上传并远端复核后，才把对象键作为成功结果对用户发布。如果只上传一份，会补偿删除；清理失败则写记录后台重试。

### 高频问题 8：为什么本地校验后还要远端复核？

> 本地校验只能证明编译产物正确，不能证明对象存储上传完整。重新读取 MinIO 并用 PDFBox 验证大小和页数，可以发现上传或对象存储层问题。

### 高频问题 9：严格资料模式和通用知识模式怎么区分？

> 严格模式要求每题都由给定 segment 支持并引用来源；资料不足时返回整体 insufficient，不生成部分卷。允许通用知识时只能在资料不足以满足题型/题量时补缺，题目需显式标记 `usesGeneralKnowledge=true` 且课程来源为空。

### 高频问题 10：14 条 Golden Case 能证明什么？

> 它能证明固定输入与当前模型配置下，覆盖的 14 类场景没有执行失败，并达到报告中的结构、引用和 PDF 指标；不能证明所有课程、所有模型版本或生产流量下都可靠。重要度一致率仍只有 50%，项目如实保留了这个边界。

### 高频问题 11：E2E 和 Golden Case 有什么区别？

> Playwright E2E 验证浏览器到后端、MQ、模型和结果展示的主流程；Golden Case 更关注固定内容样例上的 AI 输出质量与引用指标。一个偏系统链路，一个偏模型行为，两者不能互相替代。

### 容易说错

- “原子发布”不等于对象存储事务。
- 不要说质量规则能完全防止语义改写抄题。
- 不要说 14 条样例代表生产准确率。
- 不要声称模拟卷支持图片题、复杂图表题或在线自动评分。

## 一道问题的推荐回答结构

遇到“为什么这样做”时，用下面顺序回答：

1. **场景约束**：文件大、任务耗时、模型可能失败、结果需要引用。
2. **当前方案**：点出 2 到 4 个真正决定正确性的机制。
3. **失败路径**：说明超时、重复消息或跨存储失败时怎样处理。
4. **替代方案**：说出为什么当前阶段没有选，以及何时会改选。
5. **边界**：主动指出未验证或未实现的部分。

示例：

> 我用了 RabbitMQ 不是因为任务多，而是 OCR、Embedding 和出卷会显著超过普通 HTTP 请求时长，且用户离页后仍要继续。任务先在 MySQL 进入 PENDING_PUBLISH，再通过 publisher confirm 进入 QUEUED；消费者用 CAS 抢占、manual ack 和 checkpoint 执行。在至少一次投递下依靠稳定 ID 和业务幂等处理重复消息。当前没上 Outbox，是因为 MVP 更看重实现和运维复杂度；生产化时会用 Outbox 收窄数据库提交与消息发布之间的失败窗口。
