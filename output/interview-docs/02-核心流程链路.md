# FinalWeek 核心流程链路

## 1. 登录与请求安全链路

```text
输入邮箱
  -> Redis 冷却时间与窗口限流
  -> SMTP/Mailpit 发送验证码
  -> Redis 保存带 TTL 的验证码和失败次数
  -> 验证成功后创建 Spring Session
  -> 浏览器保存 HttpOnly Cookie
  -> 写请求携带 CSRF Token
```

设计要点：

- Session 放在 Redis，后端不需要自定义 JWT 撤销和刷新逻辑。
- HttpOnly 降低脚本读取 Cookie 的风险；SameSite=Lax 和 CSRF Token 共同保护写请求。
- Redis 不可用时认证链路 fail closed，而不是绕过 Session 校验。

## 2. 大文件分片上传链路

### 初始化

前端提交文件名、大小、可选 SHA-256、资料类型和重点说明。后端校验课程归属和格式，按固定 chunk size 计算分片数，在 Redis 创建带 TTL 的上传元数据。

### 上传分片

```text
PUT chunk N
  -> 校验 uploadId 归属
  -> 校验分片序号和精确字节数
  -> 写 MinIO 确定性键 uploads/{uploadId}/chunks/{N}
  -> 写成功后把 N 加入 Redis Set
```

顺序必须是“对象存储成功后再记录完成”。反过来会出现 Redis 显示分片存在，但 MinIO 实际没有对象的假完成。

相同分片重复上传会覆盖同一个对象键，Redis Set 也不会重复计数，因此上传天然可重试。

### 断点续传

前端刷新后调用上传状态接口，获取 Redis 中的已完成分片集合，计算 `0..N-1` 的差集，只上传缺失分片。

### complete

```text
查询 Redis/MySQL 完成记录
  -> 获取 uploadId Redisson 锁
  -> 再查完成记录（double check）
  -> 校验所有分片存在
  -> 按序合并到临时文件并流式计算 SHA-256
  -> 校验总大小、声明哈希与文件魔数/内容
  -> 获取 courseId + contentHash 锁
  -> 检查课程内重复资料
  -> 上传最终 MinIO 对象
  -> MySQL 事务创建 Material + BackgroundTask + UPLOADED checkpoint
  -> 清理临时分片并写 completed 标记
  -> 投递 RabbitMQ
```

两把锁解决不同问题：

- `upload-complete:{uploadId}`：防止同一上传会话并发合并。
- `material-hash:{courseId}:{hash}`：防止不同上传会话同时提交同一课程的相同文件。

但最终兜底仍是数据库完成记录和课程内内容哈希约束，锁不是唯一正确性来源。

## 3. 任务投递链路

创建业务记录与任务后，任务初始为 `PENDING_PUBLISH`。

```text
PENDING_PUBLISH
  -> 取得用户级/全局限流令牌
  -> 发布 persistent RabbitMQ 消息
  -> 等待 publisher confirm
  -> CAS 更新为 QUEUED
```

投递失败或 confirm 超时时，任务进入 `PUBLISH_FAILED`，业务记录不回滚。用户可以显式重新投递，后台也会扫描长期停留的 `PENDING_PUBLISH`。

为什么不直接“先发 MQ，再写数据库”：消费者可能先执行，却找不到数据库任务。为什么不把数据库事务一直保持到 confirm：会放大事务时间和锁占用，而且仍不能获得真正的跨系统原子性。

项目没有实现 Transactional Outbox。当前方案更轻，但存在数据库提交成功后进程立刻崩溃的窗口，需要 stale scanner 和人工重投补偿。

## 4. Consumer 状态机与重试链路

消息包含 `taskId`、`taskType`、业务 ID、课程 ID 和 `executionRound`。

```text
收到消息
  -> MySQL CAS claim 当前轮次
  -> 终态或旧轮次消息直接 ack
  -> 获取短期任务锁
  -> 根据 TaskType 选择 TaskPipeline
  -> 从 checkpoint 后继续执行
  -> 成功：MySQL 标记结果和任务 SUCCEEDED，再 ack
  -> 临时异常：RETRYING + nack(requeue=true)
  -> 永久异常/预算耗尽：FAILED + reject，进入 DLQ
```

`executionRound` 用于隔离手动重试后的新一轮任务。旧轮次的延迟消息即使到达，也不能消耗新轮次预算或覆盖新状态。

两类预算分开：

- API attempt：一次阶段内调用外部模型的重试次数。
- delivery attempt：整个任务从 RabbitMQ 被重新执行的次数。

永久错误（格式不支持、模型输出经修复仍非法）不应盲目重试；网络超时、429、第三方 5xx 才进入有限重试。

## 5. 资料解析与知识入库链路

### CONTENT_EXTRACTED

```text
PDF  -> PDFBox 按页抽取 -> 低文字密度页 OCR
PPTX -> POI 按页抽取 -> LibreOffice 预览 -> 必要时 OCR
TXT/MD -> 段落抽取
MP3 -> FFmpeg/ffprobe -> 音频切分 -> ASR
MP4 -> 音轨 ASR + 关键帧抽取 + 感知哈希去重 + OCR -> 时间线合并
```

结果统一为 `CourseContext`，单元携带页码、幻灯片号、段落号或时间戳。中间结果保存为 MinIO 中确定性 JSON 对象，再提交 `CONTENT_EXTRACTED` checkpoint。

### CHUNKED

语义分块器优先沿标题、段落和时间边界切分，超长内容再按 token 上限和 overlap 拆分，写入 `course_segment`。`(materialId, chunkNo)` 唯一，重复执行使用稳定 ID/upsert。

### EMBEDDING_COMPLETED

按批调用 Embedding，把 segment 稳定 UUID 作为 Qdrant point ID；随后对该资料的全部 segment 做 Lucene 增量 upsert。只有两个索引都完成并提交 checkpoint 后，资料才最终变为 `SUCCEEDED`。

即使中途已有部分向量，检索回查 MySQL 时也只接受成功资料，因此不会暴露半成品。

## 6. 混合检索链路

```text
问题
  |-- Embedding -> Qdrant TopK --------|
  `-- 原始关键词 -> Lucene BM25 TopK --|-> RRF -> 去重 -> MySQL 回查 -> Final TopK
```

RRF 只依赖各路排名，不要求向量相似度和 BM25 分数处于同一量纲：

```text
score(d) = sum(1 / (K + rank_i(d)))
```

默认 `K=60`。单路故障时降级到另一条；双路失败才返回 `RETRIEVAL_UNAVAILABLE`。

回查 MySQL 的意义：

- 验证 segment 的用户和课程归属；
- 过滤未成功或已删除资料；
- 获取可信原文和来源位置；
- 不直接信任向量 payload 或 Lucene 文档作为业务真相。

## 7. 知识版本与提纲发布链路

用户确认资料完成后：

```text
锁课程
  -> 确认无活跃上传/解析任务
  -> 收集全部 SUCCEEDED 资料
  -> 对 materialId + contentHash 计算集合哈希
  -> 拒绝重复集合
  -> 创建不可变知识版本与版本资料映射
  -> 创建 GENERATE_OUTLINE 任务
```

提纲 Pipeline：

```text
固定版本的 materialIds
  -> 混合检索重点/真题/教师强调片段
  -> CONTEXT_RETRIEVED checkpoint
  -> LLM JSON 生成
  -> JSON Schema + Java Validator + 来源白名单
  -> 失败时只允许一次格式修复
  -> OUTLINE_GENERATED checkpoint
  -> 事务发布节点
  -> generationVersion/CAS 校验
  -> 切换 course.currentKnowledgeVersionId
```

发布成功前，旧知识版本和旧提纲继续可用；失败任务不能把当前结果清空，旧任务也不能覆盖新版本。

## 8. 复习计划链路

```text
考试日期 + 每日分钟 + 掌握程度 + 目标成绩 + 幂等键
  -> 限流
  -> 固定知识版本、提纲和预期计划版本
  -> 创建请求与 GENERATE_PLAN 任务
  -> 202 返回
  -> LLM 生成每日任务 JSON
  -> 校验节点 ID、日期、单日预算、总预算
  -> CAS 发布新计划
```

同一幂等键重复提交返回原请求；生成失败保留旧计划；较老请求的预期版本不匹配时不能覆盖新计划。

## 9. 课程问答链路

```text
用户问题
  -> 同一事务保存 PENDING 消息和隐藏 ANSWER_CHAT 任务
  -> 202 返回
  -> 对当前全部成功资料做混合检索
  -> 取最近 N 条成功历史
  -> LLM 输出 answer + sourceSegmentIds + generalKnowledgeSupplement
  -> Validator 检查引用只来自本次上下文
  -> MySQL 再校验来源归属
  -> 保存助手消息并将问题置为 SUCCEEDED
```

检索为空时不调用模型，直接返回“课程资料不足”。问答不做 token 流式输出；SSE 推送的是任务状态，而不是模型 token。

## 10. 模拟卷链路

```text
题型/题数/分值/范围/时长/严格资料模式
  -> 固定知识版本和提纲节点
  -> REQUIREMENTS_ANALYZED
  -> 提纲来源 + 多查询混合检索构造上下文
  -> QUESTIONS_GENERATED
  -> JSON Schema/Java Validator 校验结构、题数、分值、答案、公式、来源
  -> QualityChecker 检查原题复刻、历史相似度和范围覆盖
  -> PAPER_VALIDATED
  -> 同一 DTO 渲染 paper.tex 和 answer.tex
  -> XeLaTeX -no-shell-escape 编译
  -> 校验本地两份 PDF
  -> 上传 MinIO 并重新下载复核
  -> 两份对象都成功后记录对象键
  -> PDFS_GENERATED / SUCCEEDED
```

如果只成功上传一份 PDF，系统尝试删除已上传对象；即时清理失败则写清理记录，后台重试。这里的“原子发布”指业务层只有两份 PDF 都完成才对用户发布，不代表 MinIO 本身支持跨对象事务。

## 11. SSE 与断线恢复链路

任务状态变化后：

```text
MySQL 更新任务终态
  -> Redis/SSE 发布进度事件
  -> 前端收到 event
  -> GET /tasks/{taskId} 获取权威详情
  -> 更新全局任务抽屉和对应业务页面
```

页面刷新时，前端先查询 MySQL 支撑的活动任务 REST 接口，再重连 SSE。SSE 丢事件不会造成任务状态丢失。
